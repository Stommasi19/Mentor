Each run starts from the same unfinished `starter/` project. Baseline and policy
use the same task and rules/takeover text, including a learner approach and boundary
prediction. Their initial questions differed in wording; both requested the same
decisions. Baseline's asynchronous question delayed completion; its single
follow-up was sent after the initial turn completed. `matched-inputs.json` verifies
that the two learner messages are identical across the final pair. No policy or
reference solution was added to the baseline. No persistent preferences existed
to carry between runs.

The observer reviewed each candidate's `ExpenseTotals.cs`, project file, generated
verification program, and README, plus its diff from the starter:

- **Names and flow:** all four use the domain names `expense`, `category`, and
  `month`, a decimal `total`, one scan, and a direct matching condition. The flow
  is traceable without auxiliary abstractions or infrastructure.
- **Correct boundary:** year and month comparisons exclude adjacent months and
  other years while supporting December 9999. Independent checks include month
  edges, empty labels, a year boundary, and the final representable month.
- **Useful comment:** each code output explains why comparing calendar components
  avoids constructing an unrepresentable next-month date. This records a real
  constraint at the condition, rather than narrating the loop.
- **Public contract:** XML documentation describes case-insensitive ordinal
  matching, significant whitespace, refunds, decimal arithmetic, date selection,
  zero matches, and non-null inputs. Documented decimal overflow matches native
  behavior; no hidden null-handling rule was imposed by the independent checks.
- **Usable docs:** each README records the rules and a runnable package-free
  verification command. Policy, hook, and agreement examples also illustrate
  matching or refunds. Actual generated checks were inspected separately from
  the observer's independent checks.

Both baseline and policy meet the readability/documentation criteria. The sample
does not show an improvement in code quality. The conditional offer is observable
conduct in the policy transcript, not proof of an educational benefit.

The final independent suite has nine main cases and two reserved cases. A stronger
large-decimal case was added after the initial 10-case runs to detect lost small
amounts during binary floating-point accumulation; every candidate was rerun.
The unchanged policy had already stabilized before the reserved examples ran.
Future prompt tuning must use new reserved examples rather than treat these as
still unseen.

Two deliberate disposable mutations prove useful failure detection: removing the
year comparison fails the other-year case (107 instead of 7), and accumulating
money as `double` fails the large-decimal case (0 instead of 0.01). Each mutated
candidate passes only 8/9 main checks and exits nonzero. Neither mutation is in
the repository or the passing candidates.

## Corrections and excluded attempts

- The first baseline discovered personal skills despite `--ignore-user-config`.
  It was interrupted and excluded. Subsequent runs explicitly disabled discovered
  skills, plugins/apps, and project instruction loading. The rendered prompt and
  actual baseline transcript were checked for absence of the Mentor core.
- A premature baseline resume failed because the original CLI still owned the
  thread. A queued follow-up plus the eventual explicit resume duplicated the
  learner reply. That run was excluded after transcript inspection. A third fresh
  baseline received one reply after its initial turn ended; its two learner
  inputs match the policy run. Excluded artifacts and errors were retained.
- Reusing the C# check project's build directory initially produced a missing
  reference-assembly error. `check.py` now uses fresh observer output and a forced
  candidate rebuild. The failure log is retained; all four final candidates pass
  through that helper.
- `codex debug prompt-input` did not execute lifecycle hooks, even after trust.
  Its empty policy result is not a negative host-delivery test. Actual turns and
  native hook receipts supply the positive and negative evidence above.
- The initial lifecycle observer waited for the deprecated `thread/compacted`
  notification after native compaction had already completed. It was corrected to
  wait for the `contextCompaction` item and completed turn, then rerun in a fresh
  session. That failed observer run remains in the private artifacts.

## Reproduction and test value

Use the [fixture instructions](../../fixtures/expense-summary/README.md) and
[adapter instructions](../../adapters/codex/README.md). Copy only starter sources
and the public task to each fresh external workspace. Keep checks, policy, cards,
and other outputs out of the actor's working copy. Shared filesystem access is
still possible here, so this is a development simulation.

For the controlled pair, keep CLI/model settings identical. Both runs used
`--ignore-user-config --ignore-rules --skip-git-repo-check --json`, disabled hooks,
plugins/apps and multi-agent tools, `project_doc_max_bytes=0`, and no web search.
Disable discovered local skills with per-skill `skills.config` overrides; ignoring
the user config alone is insufficient. Supply the core only through the explicit
`developer_instructions` override in the policy condition. Select response cards
based on actual questions; preserve commands/settings and both successes/failures.
The private `run_turn.py` and command JSON files record these one-off runs.

For host verification, keep the policy out of the prompt, use the reviewed project
hook, and record native execution/context, not just handler JSON. The private
`run_hook.py` and `lifecycle.py` record the one-off native client calls. Normal
interactive resume, clear, and compact can exercise the same runtime; re-review
the hook if its definition or workspace location changes. These experiment
scripts are evidence aids, not a product evaluation runner or runtime dependency.
